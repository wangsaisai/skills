# MEA Cross-Session：跨会话消息版"管理-执行-审计"工作流

这是 **mea-coding**（单会话版 MEA 编码工作流）的复制改造版。论文根基相同（LongHorizon-Harness，arXiv:2608.01964），差异在于**实现载体**：

> mea-coding 是一个会话里"一个人分饰三角"；本 skill 是"三个角色住在不同会话，靠跨会话消息传递交班记录"——执行者每次都在**全新上下文**里干活，只有**审计报告**跨会话传递。这正是论文的"fresh-context executor + audit reports are the only cross-round memory"。

核心纪律不变，反而更强：**执行者的"我觉得做完了"不是证据，审计者的检查输出才是。** 跨会话模式下这条变成硬约束：执行者会话干完就结束，它的自述只能以消息形式存在，且永远不被直接信任。

## 何时用 / 何时不用

**用**：你有 ≥2 个可互发消息的 Claude Code 会话/终端（v2.1.224+）；任务跨多轮子任务、每轮边界清晰；想每轮在全新上下文执行（防上下文腐化）；想并行推进多个互不冲突的子任务；长任务跨天、需要中途恢复。

**不用**：单会话短任务（直接做或 mea-coding）；没有跨会话消息能力时（本 skill 的协议无法落地）；子任务之间强耦合无法切分时。

## 会话拓扑（三班倒，住不同办公室）

| 角色 | 会话 | 寿命 | 职责 |
|---|---|---|---|
| 管理者（Manager） | 管理者会话 | **长期存活**，唯一持有账本 | 读账本、写子任务契约、发 CONTRACT、收 AUDIT_REPORT、记账 |
| 执行者（Executor） | 执行者会话 | **每轮新建**，干完即止 | 只收 CONTRACT，在全新上下文执行，发 EXEC_REPORT |
| 审计者（Auditor） | 审计者会话 | **每轮新建**，验完即止 | 只收 CONTRACT + EXEC_REPORT，只读验证，发 AUDIT_REPORT |

- **文件系统是唯一持久记忆**：账本落盘为 `TASK_STATE.md`（在共享工作区），任何会话被杀/消息丢失后都从它恢复。消息只是"触发信号"，不是记忆。
- 执行者/审计者会话**不持有账本**：它们只拿到当前契约相关的那几行状态和证据引用，避免把整个任务历史灌进每个会话。

## 第 0 步：开工前立契约（管理者会话）

拿到任务先别动手，把账建立起来（与 mea-coding 相同）：

- **需求清单 R1..Rn**：从任务描述拆出的每一条要求。
- **每条需求的可核验验收标准**：必须能用"读文件 / 跑命令 / 看 diff"判定真假。
- **边界约束**：明说不能改的文件、不能删的东西、不能引的新依赖。
- **初始化 `TASK_STATE.md` 账本**（跨会话落盘，格式沿用 mea-coding）：

| 编号 | 条目 | 状态 | 证据 |
|---|---|---|---|
| R1 | remember-me 登录流程 | ✓ verified | npm test 通过、token 从 cookie 恢复（第 2 轮审计） |
| R2 | 未登录访问受保护路由仍重定向 | ✗ pending | — |
| F1 | token 由 auth.ts 签发、签字符号是 HS256 | ✓ verified | 读过 auth.ts 34-41 行 |

状态取值：`✓ verified / ✗ pending / ⚠ blocked / ? untrusted`。条目类型：**需求 R**（目标/约束）、**工件 A**（产出的文件/改动）、**事实 F**（后续轮次需要的环境事实）。

## 消息协议（本 skill 的核心新增）

三种消息，格式固定，**严格区分信任级别**：

```
CONTRACT #n → 执行者会话
- 目标：只做 <X>，不碰 <Y>。
- 验收标准（≤3 条、可核验）：
  1. <命令> 输出包含 <…>
  2. <路径> 存在且包含 <…>
  3. git diff --stat 仅涉及 <…>
- 边界：不改 <A>；不加新依赖。
- 相关证据：<F/A 编号 + 文件路径>（引用，不粘贴大段历史）
```

```
EXEC_REPORT #n → 审计者会话
- 做了什么：<一句话>
- 改了哪些文件：<路径列表>
- 自测输出：<命令 + 真实输出尾部>
（本消息只陈述事实，不包含"我认为已完成"的结论）
```

```
AUDIT_REPORT #n → 管理者会话
- 完成状态：complete / incomplete / blocked
- 完整性状态：clean / suspect / violation
- 逐条验收判定：<每条验收标准 ✓/✗ + 证据引用（文件路径、命令输出尾部）>
- 可入账的事实：<F/A 条目建议 + 证据>
```

**三条铁律**：

1. **只有 AUDIT_REPORT 能改账本**。CONTRACT 和 EXEC_REPORT 只是工作流转，不是证据。
2. **消息永不携带原始对话轨迹/内部推理**。传轨迹 = 把上下文腐化从会话内搬到会话间，问题原封不动。
3. **AUDIT_REPORT 必须带证据引用**（文件路径、命令真实输出），不能只写结论——否则下一个会话无法复核，账本会积累不可信的"已验证"。

## MEA 循环（每轮 = 一次跨会话交接）

```
M — 管理者会话：读 TASK_STATE.md，选一条 ✗ pending 且前置依赖满足的需求，
    写契约，发 CONTRACT #n → 执行者会话
E — 执行者会话：收 CONTRACT，全新上下文只做契约内的事（不越界），
    干完发 EXEC_REPORT #n → 审计者会话，会话结束
A — 审计者会话：收 CONTRACT + EXEC_REPORT，只读验证（见验证速查），
    发 AUDIT_REPORT #n → 管理者会话，会话结束
记账 — 管理者会话：收 AUDIT_REPORT，只把 ✓（附证据）写入 TASK_STATE.md，
     ✗ 记 pending、⚠ 记 blocked（写一句卡点），进入下一轮
```

### 终止条件

- 所有需求 `✓ verified` → 管理者做一次**总审计**（完整测试套件 + diff 总览 + 对照用户最初验收），输出完成总结。
- `⚠ blocked` 无法推进 → 停下，告诉用户卡点与可选方向。
- 需要用户决策/新信息 → 停下来问，一次只问最关键的一个问题。
- 轮数上限（默认约 8 轮；任务特大与用户约定 ×）。

## 审计者怎么做（验证手段速查，沿用 mea-coding）

| 想验证的事 | 用什么验证 |
|---|---|
| "实现了" | 读相关文件切片 + 跑该模块测试 |
| "测试通过" | 贴出测试命令的**真实输出尾部** |
| "只改了这些" | `git diff --stat` + `git diff` + `git status --short`（含未跟踪文件） |
| "没破坏别的" | 跑既有完整测试套件 |
| "下载/生成的文件好了" | `ls -la`、校验 md5/规模 |
| "文档/报告内容对" | 打开文件读内容，而非仅确认存在 |
| "与需求一致" | 用户原话与产出并排对照 |

## 常见失败模式

**沿用 mea-coding 的 8 条**（自我宣告、一轮塞太多、会话越聊越糊、顺手越界、死磕卡点、交"完成"没证据、契约外悄悄新增文件、大改前不先测行为不变基线）。

**跨会话模式新增的 6 条**：

9. **传轨迹而非状态**：会话间转发整段对话历史 → 立刻犯"上下文腐化"，只准传契约/报告/证据引用。
10. **消息不带证据**：AUDIT_REPORT 只写"通过了" → 下个会话无法复核，账本可信度崩塌。必须附文件路径/命令输出。
11. **审计会话自说自话**：审计者用与执行者同样的模型、同样的视角"确认"结果 → 等于没人审计。审计必须只读、对照验收标准、从环境取证据（读文件/跑命令），不采信自述。
12. **消息丢失/会话被杀**：一切以 `TASK_STATE.md` 为准恢复；管理者会话重读账本即可继续，不靠聊天记忆。执行者会话被杀 → 重发 CONTRACT 重跑该轮。
13. **僵尸会话空转**：给每轮设预算（如执行 1800s、审计 300s 或等价的轮次/消息上限）；超时未回 AUDIT_REPORT 视为该轮 failed，记 ⚠ 后决定重试或终止。
14. **并行执行者抢同一环境**：两个执行会话同时改同一仓库会互相踩踏。要么串行（同一时间只有一个执行者会话），要么在 CONTRACT 里显式分区（不同目录/文件），并在 TASK_STATE.md 里登记"谁在改哪块"。

## 中途新需求

用户中途新增的任何要求**都不进当前执行轮**：把当前轮收尾（或明确暂停），先把新要求作为新的 R 记入 `TASK_STATE.md`、给编号，后续轮次按优先级处理。绝不在执行者会话干活中途"顺手实现"。

## 一个最小可跑的例子

```
（管理者会话）契约 #2：实现 remember-me 的 token 保存与恢复
  → 发 CONTRACT #2 → 执行者会话
（执行者会话）干活：写 cookie 逻辑 + 测试 → 发 EXEC_REPORT #2 → 审计者会话
（审计者会话）npm test 贴输出；读 src/auth.ts 确认 setToken()；
  git diff --stat 核对范围 → 发 AUDIT_REPORT #2 {complete, clean, 证据: tests/remember_me.test.ts 2 用例通过}
（管理者会话）TASK_STATE.md: R1 → ✓ verified（附证据）→ 下一轮
```
