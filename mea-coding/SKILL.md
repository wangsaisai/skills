# MEA Coding：管理-执行-审计编码工作流

此 skill 把论文《LongHorizon-Harness: Advancing Long-Horizon Agents for Real-World Tasks》（arXiv:2608.01964）的核心论点落到日常编码协作中：

> 长任务的失败很少因为"单步不会做"，而是因为**目标漂移、上下文越来越乱（信息难找）、以及"干活的人自己给自己验收"**这三点。解法是：把"记账的人"和"干活的人"分开，并且只允许**外部可验证的真实证据**去更新账本。

本 skill 不改变你写代码的方式，只改变**组织任务的方式**：每轮一小步、每步一张契约、每步一次独立验证，跨轮只携带紧凑的任务状态——防止上下文腐烂、防止错误自我评估传染。

## 何时用 / 何时不用

**用**：跨多文件、多阶段、需要长调试链的任务；重构；需求多且验收标准关键的任务；用户想中途核对进度；修复一串相互关联的问题。
**不用**：改一个 typo、改一个函数、单文件小修、短会话里的一次性小任务——流程是负担，直接做。

## 三个角色（由你扮演，但视角必须分离）

1. **管理者（Manager）**：只读"账本"（任务状态），决定下一步做哪个**有界子任务**，写出契约。管理者不写代码。
2. **执行者（Executor）**：只执行这张契约，产出改动 + 一条简短执行报告（"做了什么、改了什么、我自测通过"）。
3. **审计者（Auditor）**：**与执行者视角隔离**：不采信执行者的自述，改用**只读手段**（读文件、跑测试、查 git diff、执行验证命令）逐条对照契约验收。

核心纪律：**执行者的"我觉得做完了"不是证据，审计者的检查输出才是。**

## 第 0 步：开工前立契约

拿到任务先别动手写代码，先把账建立起来：

- **需求清单 R1..Rn**：从任务描述拆出的每一条要求。
- **每条需求的可核验验收标准**：必须能用"读文件 / 跑命令 / 看 diff"来判定真假。例如："`npm test` 通过，且新增了 `tests/remember_me.test.ts` 两个用例"而不是"登录更流畅"。
- **边界约束**：明说不能改的文件、不能删的东西、不能引的新依赖。
- **初始化任务状态账本**（见下）。

账本是会话内的表格即可；任务很长（可能跨多次会话/很久）时落盘为一个 `TASK_STATE.md` 文件以便中途恢复。

账本条目格式（状态取值：`✓ verified / ✗ pending / ⚠ blocked / ? untrusted`）：

| 编号 | 条目 | 状态 | 证据 |
|---|---|---|---|
| R1 | remember-me 登录流程 | ✓ verified | npm test 通过、token 从 cookie 恢复（第 2 轮审计） |
| R2 | 未登录访问受保护路由仍重定向 | ✗ pending | — |
| F1 | token 由 auth.ts 签发、签字符号是 HS256 | ✓ verified | 读过 auth.ts 34-41 行 |

- **需求 R**：要完成的目标或要遵守的约束（源自用户原话）。
- **工件 A**：产生的文件/改动记录。
- **事实 F**：后续轮次需要用到的环境事实（"签名是 X"、"依赖在 package.json 里"）。

## MEA 循环

每一轮都只推进**一个**子任务，然后回到账本选下一个。

### M — 管理

- 读账本 + 用户原话，选一条 `✗ pending` 且前置依赖已满足的需求。
- 写下**子任务契约**：目标、验收标准（≤3 条、可核验）、边界。给用户看（或至少固守住，不要中途换）。

### E — 执行

- 只做契约内的事：不越界、不顺手改别的。
- **新增任何文件（测试、脚手架、文档）都要在契约里预先声明为工件 A**，不能悄悄产生；临时验证脚本用 `node -e`/一条命令替代，不落盘。
- 完成后写一句话执行报告（这是"自述"，不等于完成）。

### A — 审计

切换"审计者"，实践**只读验证**（不是凭感觉）：
- 执行验证命令：`npm test` / `pytest` / 相关编译检查，并**贴出真实输出**。
- 读相关代码片段，确认实现与契约一致。
- `git diff --stat` 与 `git diff` 核对改动范围；**同时检查 `git status --short` 中的未跟踪文件**——未跟踪文件说明契约外悄悄产生了新内容，需拦下确认。
- 若要求"不得破坏 X"，把 X 之前的测试也跑一遍。
- 逐条对照验收标准判定：`✓ verified（有证据）` / `✗ incomplete（差什么，因什么）` / `⚠ blocked（环境、外部依赖、需用户决定）`。

### 记账

- 只有 `✓` 的结论能进账本（附证据位置）。
- `✗` 记 `pending`、`⚠` 记 `blocked` 并写一句"卡在什么上"。
- 然后进入下一轮或结束：当所有需求 `✓` 时，做一次**总审计**（完整测试套件 + diff 总览 + 对照用户最初验收），输出完成总结。

### 终止条件

- 所有需求 `✓ verified` → 总审计后收尾。
- 卡住无法推进（`⚠ blocked`）→ 停下，告诉用户卡点与可选方向。
- 需要用户决策/新信息 → 停下来问，一次只问最关键的一个问题。
- 轮数上限（默认最多约 8 轮；任务特大可与用户约定 ×）。

## 子任务契约模板

```
契约 #n：<一句话目标>
- 目标：只做 <X>，不碰 <Y>。
- 验收标准：
  1. <命令> 输出包含 <…>
  2. <路径> 存在且包含 <…>
  3. git diff --stat 仅涉及 <…>
- 边界：不改 <A>；不加新依赖。
- 相关证据：上轮的 <F/A 编号>
```

示例：

```
契约 #2：实现 remember-me 的 token 保存与恢复
- 目标：登录成功后把 token 写入 cookie，并能在刷新后恢复，仅此。
- 验收标准：
  1. npm test 通过，tests/remember_me.test.ts 有 2 个用例断言 cookie 读写
  2. src/auth.ts 中出现 setToken() 调用
  3. git diff --stat 只涉及 src/auth 与 tests 两个目录
- 边界：不动服务端路由、不改任何中间件。
- 证据：F1（auth.ts 签发 token、HS256）→ 上一轮核实。
```

## 审计者怎么做（验证手段速查）

| 想验证的事 | 用什么验证 |
|---|---|
| "实现了" | 读相关文件切片 + 跑该模块测试 |
| "测试通过" | 贴出测试命令的**真实输出尾部** |
| "只改了这些" | `git diff --stat` + `git diff` + `git status --short`（含未跟踪文件） |
| "没破坏别的" | 跑既有完整测试套件 |
| "下载/生成的文件好了" | `ls -la`、校验 md5/规模 |
| "文档/报告内容对" | 打开文件读内容，而非仅确认存在 |
| "与需求一致" | 用户原话与产出并排对照 |

## 常见失败模式（对照论文逐条规避）

1. **自我宣告**："我说改完了" → 一律不算，以测试输出与文件内容为准。
2. **一轮塞太多子任务** → 一轮一张契约，做完再选下一个，防止中途换目标。
3. **会话越聊越糊**：每轮结束把账本压缩成那一行状态表；会话超长时落盘 TASK_STATE.md，继续时读完账再动手。
4. **顺手越界**：契约的第三个文件中列了边界，用 git diff 自我检查。
5. **死磕一个卡点**：一契约反复失败两次以上 → 转出给用户告警，说明"为什么卡、可能的替代方案"，由用户选路，别闷头新换。
6. **交"完成"没有证据**：收尾必须附带验证输出，用可数断言（测试数、文件行、检查点个数）。
7. **契约外悄悄新增文件**（iteration-1 实测：对照组把 login.test.js 留在未跟踪状态）：新文件必须在契约中声明为工件 A 并纳入 git；审计时用 `git status --short` 抓未跟踪文件。
8. **大改前不先测"行为不变"基线的可核验标准**：重构类任务把"外部行为不变"落成具体断言（既有测试全绿 + API 形状对比），而不是口头承诺。

## 中途新需求

用户中途新增的任何要求**都不进当前执行轮**：把当前契约收尾（或明确暂停），先把新要求作为新的 R 记入账本、给编号，后续轮次按优先级处理。绝不在干活中途"顺手实现"。
